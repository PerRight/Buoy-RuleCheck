# 2026-10-27 통합 설치 패키지 검증 기록

## 대상

사용자 요청: "다른 컴퓨터에는 Python·C#(개발 도구)이 없을 것이니 한 번에 설치되게".
결정(사용자 답): 오프라인 통합 패키지, AutoCAD 2025·2026도 지원.

- `tools/package/make_package.py` — 개발 PC에서 패키지를 만든다.
  1. 플러그인을 2027용(.NET 10)과 2025·2026용(.NET 8)으로 빌드한다.
  2. 내장 Python을 받는다(서명 확인, `._pth`에 `..\engine` 추가).
  3. 엔진·샘플·번들 정의를 넣어 zip으로 묶는다.
- `tools/package/buoy_setup.py` — 받는 PC에서 내장 Python으로 실행하는 설치·제거 프로그램.
  1. AutoCAD 버전을 확인한다.
  2. 켜져 있는 엔진을 끈다.
  3. 설치 폴더와 번들을 한꺼번에 바꿔 끼운다.
  4. Zone.Identifier를 해제한다.
  5. 사용자 환경변수를 설정한다.
  6. 엔진 자체 시험(127.0.0.1)을 한다.
- `tools/package/payload` — `INSTALL.cmd`·`UNINSTALL.cmd`(cp949·CRLF)와 `README.txt`.
- `tools/package/tests` — 시험 18개(CI 포함).

작성은 Opus 5.5, 독립 검증은 Sonnet 5.5(Agent `model: "sonnet"`)로 2차까지 했다. 검증 폴더는 scratchpad `verify_pkg1`·`verify_pkg2`다.

이 작업 환경에서는 python.org·NuGet에 접속할 수 없고 Windows도 없다. 그래서 다음 범위까지만 확인했다.
- 가짜 내장 Python zip으로 패키지 조립
- 가짜 APPDATA·LOCALAPPDATA(한글·공백 경로)로 설치·업그레이드·제거
- 2027용 실제 빌드
- .NET 8 빌드: 가짜 참조 팩으로 복원·TFM 배관까지

**실제 Windows·AutoCAD 2025/2026/2027에서는 미확인이다.** 확인표 62~66으로 확인한다.

## 1차 검증 (697e514) → 수정 `6f7c051`

| 심각도 | 지적 | 처리 |
|---|---|---|
| 높음 | `-p:TargetFramework=net8.0-windows`를 NuGet 복원이 무시한다(assets는 net10). 그래서 .NET 8 빌드가 늘 NETSDK1005로 실패했고, 패키지가 경고 한 줄과 함께 조용히 2027 전용이 됐다. 수동 빌드 안내도 같은 이유로 틀렸다 | csproj의 `BrcTfm`(기본 net10.0-windows)이 `TargetFramework`로 들어가게 하고, 빌드는 `-p:BrcTfm=`로 한다. 2025·2026용을 못 만들면 기본은 실패로 끝난다. `--allow-2027-only`를 주면 zip 이름에 `_2027only`를 붙인다. 참조 DLL은 2025를 2026보다 먼저 찾는다 |
| 중간 | 제거의 지연 삭제를 목록 인자로 넘겨 경로 따옴표가 `\"`로 바뀌었다. 그래서 cmd가 실패해 `app` 폴더가 남았다 | 명령을 문자열 하나로 넘기고, 부모 폴더에서 이름만으로 지운다 |
| 중간 | 업그레이드 중 파일이 잠기면 엔진만 새것이고 Python은 반쯤 지워지고 번들은 옛것으로 남았다 | 옆 폴더에 다 만든 뒤 바꿔 끼운다(2차에서 두 폴더 함께 되돌리기로 확장) |
| 중간 | 이 PC의 AutoCAD용 DLL이 없는데도 '설치 완료'(종료 코드 0)였다 | 종료 코드 4와 안내 |
| 낮음 | `SendMessageTimeoutW` 인자 형식, 서명 확인 경로의 작은따옴표, `python3xx.dll` 서명 미확인, README `format()`, 로그 중복 | 모두 수정 |

## 2차 검증 (6f7c051) → 수정(이번 커밋)

H1·M1·M3은 확인됨이다. 가짜 .NET 8 팩으로 확인한 결과는 다음과 같다.
- 복원이 net8을 목표로 한다.
- DLL은 v8.0, runtimeconfig는 net8.0이다.
- obj를 공유한 채 TFM을 오가도 정상이다.
- 기본 빌드 DLL은 수정 전과 같다.

M2는 부분이었고 지적은 다음과 같다.

| 심각도 | 지적 | 처리 |
|---|---|---|
| 중간~낮음 | 옛 폴더를 비킨 뒤 새 폴더를 넣지 못하면 `app`이 사라진다(백신 잠금 등) | 그 폴더를 옛것으로 되돌린다. 이름 바꾸기는 0.4초 간격으로 다섯 번까지 시도한다 |
| 중간~낮음 | 설치 폴더와 번들을 따로 바꿔, 번들이 실패하면 엔진은 새것이고 플러그인은 옛것으로 남는다 | 두 폴더를 모두 `.new-<시각>`에 만든 뒤 차례로 바꾸고, 하나라도 실패하면 이미 바꾼 것까지 되돌린다(`swap_all`) |
| 낮음(퇴행) | 설치된 쪽 제거에서 Enter 전에 창을 닫거나 Ctrl+C를 누르면 지연 삭제가 불리지 않는다 | 지우는 프로세스를 먼저 띄운다. 1초마다 최대 60번 `rmdir`을 시도하고, 지워지면 멈춘다 |
| 낮음 | .NET 8 빌드가 ASP.NET Core 참조 팩까지 요구한다. 오프라인이면 SDK가 정한 정확한 팩 버전이 필요하다 | `DisableTransitiveFrameworkReferenceDownloads`, README에 정확한 버전 안내 |
| 낮음 | `-f`·`--no-restore` 함정, R25를 마지막에 빌드해 obj가 net8 상태로 남는다 | csproj 주석, R25를 먼저 빌드하고 R26을 마지막에 |
| 낮음 | 제거가 `.old-*`·`.new` 잔재를 지우지 않는다. `.new`가 고정 이름이라 못 지운 잔재가 이후 업그레이드를 막는다 | 제거 때 잔재 정리, 임시 폴더 이름에 시각을 붙임, glob escape |
| 정보 | 로그 빈 블록, docstring 순서·문구, 지연 삭제 이름 따옴표 | 수정 |

시험은 18개다. 이번에 추가한 것은 번들 실패 시 두 폴더 되돌리기, 새 폴더 넣기 실패 시 되돌리기, 제거 때 잔재 정리, 지연 삭제 명령 줄이다. 이 2차 지적의 수정분은 시험으로만 확인했고, 별도 3차 검증은 하지 않았다.

## 실제 Windows에서만 확인할 것

1. **실제 빌드와 로드**
   - .NET 8 참조 팩, AutoCAD 2025 DLL로 R25를 빌드한다.
   - 2025용 DLL이 2026에서 로드되는지, R26이 2027에서 로드되는지 본다.
   - `Platform="AutoCAD*"`, 같은 AppName의 두 `<Components>`가 문제없는지 본다.
2. **폴더 이름 바꾸기**
   - 실행 중인 `python.exe`나 탐색기로 연 폴더가 있을 때 이름 바꾸기가 실패하는지, 그리고 되돌리기가 되는지 본다.
   - AutoCAD autoloader가 `*.bundle.old-*`·`*.bundle.new-*` 형제 폴더를 무시하는지 본다(남는 경우는 정리가 실패했을 때뿐).
3. **명령 실행**
   - 지연 삭제의 `for /l` 반복이 실제로 지우는지 본다.
   - `tasklist`·PowerShell 출력을 cp949(`oem`)로 해석하는지 본다.
   - `Get-AuthenticodeSignature`가 PSF 서명을 `Valid`로 읽는지 본다.
   - `WM_SETTINGCHANGE` 뒤 새로 켠 AutoCAD가 `BRC_*` 환경변수를 받는지 본다.
4. **내장 Python**
   - `._pth`의 `..\engine` 경로로 `-m brc serve`(cwd=engine)와 `-c import brc`(cwd=app)가 되는지 본다.
   - AppLocker·Smart App Control이 `%LOCALAPPDATA%`의 `python.exe` 실행을 막는지 본다.
5. **.cmd 파일**
   - INSTALL.cmd·UNINSTALL.cmd가 종료 코드를 넘기는지 본다.
   - Windows '베타: UTF-8 사용'을 켠 PC에서 cp949 `.cmd`의 echo 한글이 깨지는지 본다(Python 출력은 영향 없음).
