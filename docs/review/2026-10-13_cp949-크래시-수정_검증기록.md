# 2026-10-13 CLI cp949 크래시 수정 · 독립 검증 기록

## 발견 경위
공개 커밋 전체 런타임 검증(/verify) 중 발견. `python -m garc revs ../samples/S140_rev*.dxf`를
stdout이 cp949인 환경(한국어 Windows 기본 cmd, Git Bash 파이프, `> log.txt` 리다이렉트)에서 실행하면
`_print_report`·`revs` 출력의 '—'(U+2014)에서 `UnicodeEncodeError`로 크래시. CLAUDE.md §6의
데모 명령 그대로가 환경에 따라 죽는 상태였다. PowerShell 콘솔(코드페이지 65001)에서는 재현 안 됨.

## 수정 (opus 세션)
- `engine/garc/cli.py` — `main()` 시작부에서 `sys.stdout`/`sys.stderr`를 `reconfigure(errors="replace")`.
  인코딩 자체는 바꾸지 않으므로 cp949 콘솔에서 한글은 그대로 표시되고, 인코딩 불가 문자('—'·'→'·'⚠')만 '?'로 대체.
- `engine/tests/test_robustness.py` — 회귀 테스트 `CliEncoding.test_check_survives_cp949_stdout` 추가
  (TDD: 수정 전 실패를 먼저 확인 — 실제 크래시와 동일한 `UnicodeEncodeError` 재현 후 수정).

## 독립 검증 (sonnet 옵션 서브에이전트, 저장소 무수정·별도 프로브 폴더)
| 항목 | 판정 | 근거 요약 |
|---|---|---|
| A. 수정 전 버그 실재 | 확인됨 | `git show HEAD:engine/garc/cli.py` 사본 + `PYTHONIOENCODING=cp949` 서브프로세스로 동일 크래시 재현 (U+2014, exit 1) |
| B. 수정 후 동작 | 확인됨 | `check`·`revs` 모두 exit 0, stderr 없음, 한글 cp949 정상 출력, '—' 등 11곳만 '?' 치환, 깨진 바이트 없음 |
| C. 부작용 없음 | 확인됨 | `PYTHONUTF8=1`에서 수정 전/후 `--json` 출력 바이트 단위 동일(cmp), 종료 코드(pass=0/fail=1/incomplete=2) 보존, cp949에서도 `--json`은 유효한 JSON |
| D. 테스트가 회귀를 잡는가 | 확인됨 | 수정 전 cli.py 사본으로 같은 시나리오 → 4개 단언 전부 실패 |
| E. 전체 스위트 | 확인됨 | 70개 통과 (기존 69 + 신규 1) |

## 검증자 지적과 반영
1. **주석 오류**: '≤'를 cp949 인코딩 불가 예시로 들었으나 실제로는 cp949에 존재(0xA1C2) → 주석·테스트 docstring을 '—'·'→'·'⚠'로 수정(동작 무변경, 주석만이므로 재검증 생략).
2. **참고 (미반영, 문서화만)**: cp949 파이프에서 `--json` 출력은 크래시 대신 인코딩 불가 문자가 '?'로 치환되어 데이터 손실 가능. 플러그인은 HTTP 경로(UTF-8 JSON)라 무관. CLI `--json`을 기계가 소비할 때는 UTF-8 환경 권장.
3. **참고**: `reconfigure`가 없는 비표준 스트림 환경에서는 조용히 넘어감(원래 버그 잔존 가능) — 표준 CPython 3.10+에서는 해당 없음.
